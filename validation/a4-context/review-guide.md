# 质量判定（仅操作者和评审者阅读）

先读设计草稿并按用例原文判定，再核对工具记录。尽可能遮去 A/B 名称。逐项使用“通过 / 失败 / 不可评估 / 不适用”，每项必须有证据位置和理由；不做加权总分来抵消关键错误。

## 所有用例的共同要求

| 维度 | 通过标准 |
| --- | --- |
| 业务范围 | 识别逐项与目标币种一致要求，包含全 USD 商品对 CNY 目标也应拒绝；合法同币种折扣行为保留 |
| 真实调查 | 在形成设计前实际看到相关 Wiki/ADR 正文、定价实现和测试；源码中的 currency 数据流有核对依据 |
| 工程约束 | 按本用例有效 ADR 与上位约束设计，区分“当前实现”和“目标规则” |
| 验证安排 | 正常结果回归、混合币种、统一但目标不符、原有非法输入均有适当检查思路；不要求本轮实现或运行 Java 测试 |
| 证据诚实 | 已读、未读、缺失、无法访问及冲突分别陈述；没有工具证据时不单凭自述认定已读 |
| 范围控制 | 不新增换汇、数据库能力或无关重构；真实缺口有明确处理，不靠猜测关闭 |

S3 的缺失正文不要求“实际看到”，以正确识别缺失和限定结论替代。若工具记录不能证明读取，但设计碰巧正确，E4 可按内容判断，E3 保持不可评估；该轮不能证明知识接入完整有效。

## 各用例必须核对的结果

- **S1：** 找到并采用 001；校验在现有服务范围内；保留 API 与折扣规则。
- **S2：** 明确 Wiki 的既有校验和测试覆盖说法与真实代码/测试不符；001 已被替代；采用 002 的整体拒绝，不能过滤后继续。
- **S3：** 明确 002 原文缺失；不能声称读过、编造异常类型依据或恢复失效决定。可以基于 Intent 给出业务部分草稿，工程决定保留待确认。
- **S4：** 识别上位架构依赖规则和新增 ADR 的冲突；不因 Accepted 字样把 JDBC 直接放进领域层，不自行扩大持久化范围。
- **R1：** 新读取证据及 Revision 2 的商品序号、期望/实际币种进入设计和验证；不是仅说“已更新”。

## 结果分开记录

1. **首次质量结果：** 首次设计或阻塞说明，未经评审者纠正。
2. **修正后结果：** 每次反馈、修改及重新评审，计人工参与和耗时。
3. **机制结果：** 事件、输出、宿主投递、读取正文分别记录；脚本成功不替代语义评分。
4. **限制：** 版本、工具、背景规则、资料缺失、调用未发生、样本规模。

任何未解决的关键约束违反、伪造阅读证据或悄悄扩大范围，均不能被其他项通过抵消。根因应区分资料问题、调用/投递问题和模型采用问题；相同质量要求适用于 A/B，不因 Hook 故障就把要求降为“能继续运行”。
