# AI SDLC 项目上下文与知识管理方案

[总览与下一步](../../README.md) · 知识方法 · As-Is、上下文与 ADR，按主题查阅

更新日期：2026-09-15。本文汇总本次讨论，作为后续落地的设计依据；目录和流程为建议，尚未初始化到具体业务项目。

产品化方向与阶段安排见 [AI SDLC 工具套件与插件路线图](../roadmap/ai-sdlc-plugin-roadmap.md)。本方案为其提供共用上下文与知识管理依据。文档职责、默认路径与各类产出内容集中在 [统一文档体系](../method/project-documentation-system.md)；本文细化资料选择、ADR 演进和上下文复用。

术语以 [AI SDLC 词表](../../CONTEXT.md)为准：准备阶段固定 Intent、Spec、Plan 三个步骤与三份产物；Design 是 Spec 的方案内容，Tasks 是 Plan 的任务内容。

## 1. 目标与整体思路

核心目标：让 Intent 准确保留业务侧的需求与确认，让 Spec、Plan 和代码建立在真实项目现状及适用工程依据上。**工程规范与架构决定统一用 ADR 管理，从 Spec 开始导入；Intent 默认不读取 ADR。**

当前可能直接让 Agent 读取需求文档，也可能使用 Superpowers、OpenSpec、Spec Kit 等 SDD 框架。因此，需要一套独立于具体框架的项目上下文组织方式，让不同入口可以使用同一批知识和约束。

建议采用：**统一的项目上下文入口 + 分层知识 + 按 Topic 维护的轻量 As-Is + 按变更探索与核验 + 贯穿变更的上下文记录。**

```text
业务诉求、规则与 BA 方案 → Intent：业务需求与确认
                              ↓
项目入口、ADR、As-Is、代码 → Spec：具体要求与方案
                              ↓
工程约定、实际文件与环境 → Plan：实施与验证安排
                              ↓
                       实现 → 验证与交接
                              ↓
                  按实际结果回写知识与证据
```

Intent 由 BA 整合业务来源与已有设计，必要时参考轻量现状来理解问题，技术调查可以交给 Spec。Spec 继承业务需求，再读取 ADR 和 As-Is 判断方案；Plan 结合完整 Spec、工程约定及实际代码与测试布局形成 Tasks。历史技术选择不能自动限制需求，冲突由 Spec 说明影响与处理路径；只有业务依据或决定实际变化，才由 BA 修订 Intent。Spec/Plan 产生的长期工程决定可及时进入 ADR。

本次只开发部分需求时，选材仍包括整体目标、共同业务规则、相关原型流程和公共工程方案，以及实际依赖的外部契约。共同输入记录采用版本与业务确认范围，变化时复核受影响部分；其他范围的目标或设计不能直接作为已经实现的 As-Is。Feature/Story 名称只作已有项目的可选关联，详见[范围与复用约定](../method/sdd-artifact-contracts.md#scope)。

## 2. 统一入口：用 ADR 管理项目决定与规范

本套件将 ADR 的使用范围扩展为**项目工程决策记录**，统一承载架构选择、工程约定及外部规范的工程采用决定。采用一套目录、一份模板和同一套状态管理，按架构、测试、安全等主题选择。业务需求和规则保留在业务来源及 Intent 中；不要求为了统一目录将所有业务材料改写成 ADR。

已有 ADR 若承载了业务政策或规则，保留其原位置并核验业务来源、确认权限与适用性，需要时可供 BA 引用；不能仅凭它位于 ADR 目录就赋予其业务否决权。统一载体不等于每个步骤都要读取同一组文档。Intent 与 ADR 的具体边界见[产物约定](../method/sdd-artifact-contracts.md#intent-adr)。

这是本套件的组织选择。MADR 的说明允许用模板记录其他重要决定，并提供验证决定符合性的 Confirmation 内容，可作为参考。[MADR 说明与模板](https://adr.github.io/madr/)

项目入口负责职责、词表、仓库与模块导航，连接 ADR、Topic、变更和证据。完整结构以 [统一目录](../method/project-documentation-system.md#layout)为准：项目入口是 `docs/project/README.md`，ADR 索引是 `docs/adr/README.md`，正文是 `docs/adr/<adr-id>-<slug>.md`。已有框架使用项目入口登记的映射。

支持相应机制的宿主可用简短的 AGENTS.md、CLAUDE.md 或配置引导读取总入口，核心流程使用同一套资料。

### 2.1 一份索引，同时支持当前使用与历史追溯

`docs/adr/README.md` 汇总 ADR 元数据与链接。默认先呈现当前有效、适用于相应范围的记录，其他状态仍可检索；Agent 按需追溯，无需顺序重放全部历史。

| 索引信息 | 最低内容 | 用途 |
| --- | --- | --- |
| 标识、标题、位置 | 稳定 ID、主题、正文链接 | 定位决定与条款 |
| 适用范围与触发条件 | 项目/模块/能力；必要时补路径、接口、数据类型 | 按变更影响选择 |
| 读取时机 | 工程阶段的必读项，或 Spec/Plan/实现中的相关触发条件 | 控制读取范围；不要求 Intent 全量加载 |
| 状态与生效条件 | 提议、已接受、已替代、未采纳；何时、在哪些范围生效 | 区分现行约定、候选和历史 |
| 关系 | 替代、被替代、补充、依赖哪些 ADR | 找到有效决定与背景 |

索引只维护发现所需信息，不另存一份可独立修改的规则全文。正文维护规则、理由和适用条件；后续可自动生成索引，初版手工保持一致即可。

“已接受”还要结合生效条件与范围。例如迁移完成后才启用的新约定，不应被当成所有现存模块已经采用的规则。仓库内版本由 Git 提交及实际采用的工作区修改记录；外部规范的采用版本必须可定位，不能只写“最新版”。

### 2.2 同一份 ADR 模板承载决定和规则

一份 ADR 围绕一个能独立判断和演进的决定，可以包含一组紧密相关的规则。不必为每条编码细则拆一份，也不要将全项目所有约定合成一份记录。

```markdown
# ADR-<编号> <决定标题>

- 状态、决策日期与采纳依据：
- 适用范围、生效条件与读取触发：
- 来源：原始材料，或产生本决定的变更与 Spec / Plan 章节
- 关系：替代 / 被替代 / 补充 / 依赖的 ADR

## 背景与问题
## 决定与适用规则
## 理由与重要替代方案
## 影响、代价与例外
## 如何验证符合性
## 来源与关联材料
```

规则写清必须满足什么、条件与强制程度；验证部分给出可复用的检查方法，本次是否通过仍在任务与验证记录保存。例如“采用统一 API 错误契约”记录错误结构、兼容要求和检查方式；“采用项目指定 formatter”引用配置文件中的具体规则。

详细 schema、工具配置、操作手册可作附件或来源，由 ADR 确认采用范围。这样统一决定的管理入口，也保留材料各自的权威内容。

既有规范按需纳入：

- 保留原文，用 ADR 明确采用范围、版本和来源；历史理由未知时写明未知。
- 相关变更发生时，再整理为 ADR 规则正文或继续引用固定版本的原文；明确各自负责哪些内容，避免两处独立修订同一条规则。
- 外部规范的采用和例外也由 ADR 记录，本地决定不能擅自消除外部硬约束。
- 原规范目录可保留为引用材料；新增项目约定统一从 ADR 进入，无需一次迁移全部历史。

**ADR 的决定与 As-Is 的实现状态分别核验。** 决定已接受不证明代码已实现，源码也不能证明某项约定已得到采纳。差异由 Spec 明确本次处理，Plan 安排相应工作。

### 2.3 接入不同工作流

| 启动方式 | 建议接入方式 |
| --- | --- |
| 直接读取需求文档 | 在 Agent 项目指引中要求先读取统一入口，再调查需求涉及的模块 |
| Superpowers | 通过宿主 Agent 的项目指引，将统一入口纳入项目探索和规划过程 |
| OpenSpec | 通过项目配置中的 `context` 引入公共要求，使用 `rules` 补充各产物的要求 |
| Spec Kit | Constitution 记录已认可的项目原则，项目指引关联统一入口，并在规划时检查原则符合性 |

文档中存在链接，并不意味着 Agent 已读取链接目标。接入说明应明确要求读取相关内容，后续通过产物中的来源、模块选择和方案依据判断是否落实。

上述方式需要适配具体工具的读取机制，框架不会自动继承一套外部知识库。相关依据见 [OpenSpec 项目配置](https://openspec.dev/docs/project-config)、[Spec Kit 既有项目指南](https://github.com/github/spec-kit/blob/main/docs/guides/existing-projects.md) 和 [Superpowers 项目探索流程](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)。

## 3. 适用范围与信息性质

方法层、项目知识层、变更层、证据层按文档职责划分。下面的系统、项目、模块等描述适用范围，与层次和 Git 目录边界分别判断；一个 Topic 可以横跨多个仓库，一个仓库也可能包含多个独立项目。

| 适用范围或对象 | 主要内容 | 使用方式 |
| --- | --- | --- |
| 跨项目工程规范 | 通用质量要求、协作约定、认可的工程实践 | 项目 ADR 明确采用的范围、版本和例外 |
| 产品或系统知识 | 业务术语、跨服务流程、系统边界、集成契约 | 涉及对应系统行为时读取 |
| 项目知识 | 项目职责、技术栈、架构决策、构建测试方式、模块导航 | 进入项目时读取概要，按需深入 |
| 模块知识 | 局部接口、约束、异常处理、参考实现、测试习惯 | 涉及对应模块时读取 |
| 本次变更上下文 | 本次范围、适用知识、已核验事实、决策、待确认事项 | 贯穿此次变更，随调查和实现更新 |

每条重要知识应能辨认其适用范围和来源。对版本敏感的知识，还要记录核验依据。

需要区分三类信息：

- **现状事实**：当前系统实际如何工作，由代码、配置、契约和测试等证据支持。
- **项目决定与约定**：项目要求如何实现、应遵循哪些规则，由适用 ADR 及其引用的契约和来源支持。
- **本次决策**：此次变更决定如何调整现状，以及选择的原因；满足长期复用条件时进入 ADR。

已有实现可以帮助理解项目，但可能包含历史遗留问题。参考实现应明确哪些值得复用，哪些只是兼容现状。出现事实与规范不一致时，应记录差异及本次处理方式。

局部 ADR 可以补充公共约定；需要偏离时记录明确的例外、范围和依据。更晚日期、更深目录都不自动取得优先级。冲突按采用、补充、替代关系处理；未决时只暂停依赖该决定的范围，沿用已有授权与项目治理要求。

## 4. Topic As-Is 与动态探索如何分工

首次整理 Brownfield 项目的仓库现状、为 Intent、Spec 或 Plan 准备现状依据、实施后更新主题或恢复旧任务时，读取 [Brownfield 仓库 As-Is 实施与复用指南](brownfield-as-is-implementation-and-reuse.md)。该指南细化了必要内容、证据与基线、初始化、增量维护、阶段接入及可复制模板；第一版范围限定为仓库内可验证的现状。

建议同时保留轻量 Topic As-Is 和按变更探索的能力。长期文档减少重复调查，动态探索确认本次相关实现仍然有效。

| 信息类型 | 适合的载体 |
| --- | --- |
| 业务术语、关键状态流转、兼容约束、跨模块行为 | Topic As-Is |
| 项目决定、规范条款、适用前提与取舍 | ADR，并从 Topic 引用；按状态、范围和生效条件判断如何适用 |
| 符号、定义、引用、调用关系、结构性依赖 | Codegraph、LSP、代码搜索等工具 |
| 本次涉及的真实实现、配置与影响范围 | 按变更调查，并记录证据 |
| 本次范围、方案、任务和验证结果 | 本次变更上下文及 SDD 产物 |

Topic 宜按有实际意义的业务或技术能力划分，例如身份与权限、订单生命周期、数据一致性、第三方集成。无需为每个类、函数或文件维护一篇说明。

优先沉淀以下知识：经常复用、调查成本高、行为分散、设计原因难以从代码推导，或者误解后容易导致返工的内容。从一项近期需求涉及的主题开始即可，不设固定页面数量。

一份 Topic As-Is 回答四个问题；已有 Wiki 能回答时直接复用：

```text
当前做什么：能力范围、行为和重要规则
怎样实现：入口、协作及相关数据/接口/配置
什么尚不确定：约束、例外、冲突和未知项
如何核对：来源、适用代码状态和验证入口
```

As-Is 尽量记录稳定语义和关键入口，细节通过来源定位。日常维护只设使用前核对、实施收尾回写两个时机；相关实现变化后复核需要使用的部分，单纯修改日期不能证明内容有效。八个调查方向用于查漏，不是逐页强制章节。

采用 OpenWiki 等知识工具时，直接使用原生页面、来源和更新状态，不再维护第二套事实编号、YAML 状态、指纹或路径监控表。Topic 只是主题知识页的称呼，按项目入口定位实际目录；本次专用调查留在 Spec/Plan，完整约定见[最小 As-Is 方案](brownfield-as-is-implementation-and-reuse.md#minimum)。

Codegraph 在这里泛指代码图谱或语义导航工具，其能力取决于具体实现、语言和索引覆盖。使用前应检查索引与当前代码版本的关系，并补查工作区中尚未索引的修改。动态图、反射、配置路由、消息和外部服务等依赖仍需结合配置、契约与测试确认。图中没有边，不能直接证明没有依赖。

这种“小量预加载知识 + 按需检索和探索”的组合，与 Anthropic 的[上下文工程实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)一致。语义导航和索引维护的能力示例可参考 [Sourcegraph 代码导航](https://sourcegraph.com/docs/code-navigation)及[索引工作流](https://sourcegraph.com/docs/code-navigation/how-to/adding-scip-to-workflows)。

## 5. 各步骤如何读取与演进 ADR

这里的“导入”指：**读取适用原文，判断效力与范围，把它落实到本次产物并保留来源。** 只附链接、只读取摘要或把文件加入搜索索引，都不足以完成导入。

三步的产物字段与交接要求见 [输入输出流转](../method/sdd-artifact-contracts.md#flow)。本节集中维护 ADR 的选择、采用和演进方式；ADR 属于跨变更复用的项目依据，按需产生，主线仍是三步三产物。

### 5.1 每个步骤导入哪些

Spec、Plan 和实现先读取工程入口和目录，再选择本阶段所需正文。Intent 读取业务来源，ADR 不是前置输入。已在当前上下文完整读取、版本与适用范围未变的内容可以复用；换会话、内容不可见或相关来源变化时重新读取。

| 步骤 | 读取哪些 ADR | 如何使用 | 可能回写什么 |
| --- | --- | --- | --- |
| Intent | 默认不导入；已有材料直接引用的业务条款按来源判断 | 保留业务需求、约束与确认；技术疑问可交 Spec 调查 | 由 BA 维护业务内容，不做架构符合性判定 |
| Spec | 相关架构、API、数据、安全、兼容及验证策略的决定；必要历史背景 | 核验适用性、约束与需求的冲突，形成具体要求、AC 和 Design | 新增长期工程决定的 ADR，或提出对已有决定的例外、补充、替代 |
| Plan | Spec 引用的决定；按实际文件、模块、共享依赖补读编码、测试、构建、迁移等约定 | 落实到 Tasks、依赖、检查与完成条件 | 新的可复用工程约定进入 ADR；改变关键方案时先修订 Spec |
| 实现与验证 | 当前任务及整体验证依赖的 ADR | 执行检查，保存实际证据 | 补充非语义说明和证据引用；决定实质变化按相应上游步骤处理 |

工程阶段的全局必读应是一小组普遍适用的条款；其范围不自动扩展到 BA 形成 Intent 的工作。每份 ADR 按主题和触发条件选择，无需按“规范类”和“架构类”执行两套导入动作。

Plan 的选择范围可能比 Spec 更细、更广。例如 Spec 确定事务内记录事件，Plan 定位到共享存储模块后，还需补读其迁移约定。**Plan 使用 Spec 的决定，同时继续直接使用适用 ADR 的原文。**

### 5.2 导入的具体动作

这套动作放在 Spec、Plan 及实现的生成、修订或执行流程内部，可以由人、通用 Skill 或 Agent 执行。Intent 沿用业务材料整理与确认流程。

1. **发现入口。** 读取项目总入口和统一 ADR 目录；确认参与仓库与文档位置。尚无目录时先按现有指引、README 和相关模块文档检索，建立最小导航；缺少来源如实记录。
2. **选择候选。** 根据本次目标、能力、模块、接口、数据与计划修改路径选择；加上全局必读项、相关共享依赖，以及 ADR 的替代或依赖记录。涉及迁移时也读取已接受但尚未生效的目标决定，分清现行、迁移和目标范围。单纯关键词或路径匹配只用于初筛。
3. **读取原文。** 用文件或文档读取工具将相关原文章节纳入当前步骤的上下文，连同适用条件、例外和必要前提读取；核验状态、采用版本及本次范围。关键原文不可访问时标明未读取，不声称符合，只暂停依赖它的判断。
4. **形成采用结论。** 分清 ADR 中的必须遵循条款、推荐做法、有效决定和历史参考；说明本次如何处理。ADR 与代码不一致、ADR 之间冲突或需改变既有决定时，记录差异及依据，不自行把当前实现当成豁免。
5. **写入产物。** Spec 记录工程依据对具体要求、AC 与 Design 的影响，Plan 落到 Tasks 和验证。用“来源章节与版本 → 本次处理 → 产物位置”关联，正文保留本次采用内容，原文通过引用访问。若工程选择与业务承诺冲突，先明确方案与代价；业务侧作出调整决定后才回写 Intent。
6. **检查并交接。** 检查应读材料是否遗漏、当前规则和决定是否有承接、例外是否有依据。进入下步或恢复工作时比较范围、代码和文档变化，只复核受影响部分。

发现 ADR 不适用时，通常不必逐项写“未采用”。对索引显示强相关、下游容易误用或涉及冲突的候选，保留排除理由。

结构检查可以发现失效链接、缺少版本、替代链未跟进、没有任务承接；是否选全资料、正确理解条件、满足业务与架构要求，需要结合来源和方案审查。实际合规结果由相关静态检查、测试、CI 或适当的审查证据支持，读取记录本身不能证明符合。

### 5.3 如何记录，避免每份文档复制全文

在 Spec 的“输入依据”中保存本次采用记录，Plan 引用该记录并补充执行相关来源。Intent 保留业务目标、边界与决定的来源，以及采用的 BA 需求/方案/原型位置、版本和用途，Spec 按需读取原件。已有变更上下文可承载较长的调查过程；采用结论和任务状态各有一处权威位置。

采用记录的最小字段：

| 字段 | 写什么 |
| --- | --- |
| 来源 | 文档 ID 或路径、具体章节、采用版本及当时状态；多仓库分别记录 |
| 适用原因 | 本次哪个能力、模块、行为或文件触发 |
| 本次采用与处理 | 相关规则或决定、适用条件，以及遵循方式或例外依据 |
| 承接位置 | 在 Spec 中定位要求/AC/设计项；在 Plan 中定位任务与检查，各自维护 |
| 未决项（如有） | 缺少什么、影响哪部分、如何解决 |

无需为每句规则创建新编号；能稳定引用已有章节即可。公共版本信息可记录一次，表中引用它。Plan 只维护自己新增来源与执行映射。已提炼为 ADR 的长期决定及理由在 ADR 维护，Spec 说明本次如何应用，Plan 展开具体工作；尚未提炼的本次关键决定在 Spec 维护。

**虚构示例：新增订单取消能力。** ADR-0001 规定失败取消不得改变状态，ADR-0012 规定状态变更与事件记录同事务提交，ADR-0002 规定测试覆盖事务失败与事件重试。来源版本在变更记录中分别定位。

| 来源条款 | Spec 中的采用 | Plan 中的承接 |
| --- | --- | --- |
| ADR-0001：失败操作不产生业务状态变化 | AC-02：取消失败时状态保持；Design 明确失败边界 | T-01 实现状态转换及失败处理，验证失败场景的状态不变 |
| ADR-0012：状态与事件记录同事务提交 | Design D-01 复用现有事务与事件记录机制；核验实际实现 | T-01 同事务写状态与事件记录；T-02 验证事务回滚后两者均未写入 |
| ADR-0002：测试覆盖事务失败与事件重试 | 验证策略明确失败场景与重试风险 | T-02 覆盖回滚与重试；如依赖尚无测试入口，任务先建立入口 |

这样，上游说清规则和方案，下游知道落实在哪、如何判断完成。Plan 不能只写“遵守项目规范”；Spec 也不能只列一组文档链接。

### 5.4 提供给 Agent 的通用导入指令

以下指令可放入 Spec/Plan 的 Skill 或工程流程模板，共用同一段规则；Intent 入口不执行这套 ADR 导入要求。

```text
生成或修订 <Spec / Plan> 时：
1. 读取项目上下文入口，按本次范围和当前步骤选择适用 ADR 及其引用材料。
2. 读取相关原文章节及条件，确认采用版本、状态、生效范围和替代关系。
3. 区分当前规则、既有决定、历史参考和未决项；用仓库证据单独核验实现。
4. 在当前产物记录“来源及版本—适用原因—本次处理—承接位置”。
   Spec 写需求、AC 与关键方案；Plan 引用这些决定，补充任务输入和验证。
5. 检查有没有遗漏应遵循的约束。范围、路径或来源变化时补选并复核。
   关键依据缺失或冲突时标明受影响范围；继续不依赖它的工作。
6. 检查本步新决定是否值得跨变更复用；按 ADR 演进规则补充或替代，
   同步采纳状态、索引和产物引用。只有局部执行意义的决定保留在 Plan。
```

可迁移的核心是目录约定、选择规则和产物记录。宿主自动加载规则可以协助发现；搜索、Codegraph 等工具可以给出候选。最终仍按上述步骤读取和采用，不依赖某一 Agent 的隐式上下文机制。

### 5.5 Spec、Plan 如何产生和更新 ADR

ADR 同时是输入，也是步骤内按需形成的项目知识。不要把沉淀统一推迟到交付收尾：影响下一步的决定，应在本步明确状态并关联来源，收尾再核对最终实现与文档。

**什么时候值得形成 ADR：** 决定会约束后续变更，涉及公共接口、共享机制或项目工程约定，或未来需要理解其重要取舍。普通文件位置、任务顺序、一次性调试办法保留在 Plan；普通功能行为留在 Spec。已有 ADR 足以表达时直接引用。

| 发现位置 | 例子 | 保存与回写 |
| --- | --- | --- |
| Spec | 确定以后订单状态事件均采用事务内记录机制 | 形成 ADR，Spec 的 Design 引用决定并说明本次落点；Plan 据此拆任务 |
| Spec | 本次采用的方案需要改变已有的一致性决定 | 新 ADR 记录取舍及替代范围，修订 Spec；再复核 Plan |
| Plan | 发现共享组件测试应统一采用一套 fixture 约定 | 在既有权限范围内形成工程约定 ADR；Plan 引用并安排采用工作，Spec 的验证策略受影响时同步 |
| Plan | 拆任务时发现公共事件格式必须变化 | 先回到 Spec 明确接口与兼容方案，再形成或替代 ADR，最后修订 Plan |
| Plan | 决定先改文件 A、再改文件 B | 记录为 Tasks 依赖，不创建 ADR |

“更新历史 ADR”按变化性质处理：

| 变化 | 处理方式 |
| --- | --- |
| 提议中的 ADR 还在讨论 | 原文件迭代，保留版本；它尚不自动约束其他变更 |
| 已接受 ADR 的错字、链接、非语义澄清或新证据引用 | 可原位补充，保留 Git 历史；不改变原决定、范围和强制程度 |
| 新增独立约定，或不改变旧决定的补充 | 新建 ADR，说明与已有记录的补充或依赖关系 |
| 改变已接受决定、适用范围、规则强度或关键前提 | 新建替代 ADR，写清改了什么、理由及生效条件；保留旧决定和历史依据 |

用新记录替代已改变的决定、保留旧记录及其关系，沿用 ADR 的经典做法。[Nygard：Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

新记录仍是提议时，旧 ADR 的有效性不变。新决定按项目既有决策权限与已有授权被采纳后，再同步新旧记录及索引。没有采纳依据就保持提议，不能因 Agent 写出了文件便将它宣布为全项目规则；本套件不另设统一的人工批准步骤。

替代只有在声明的范围和条件内生效。迁移期间新旧方案并存时，明确各自适用部分，不能过早将整份旧 ADR 标成失效。相关任务开始前应明确采纳状态及本次适用的现行、迁移或目标规则；迁移任务可以落实尚未生效的已采纳目标决定，不能将未来生效条件记录为已满足。

一次回写按以下顺序收口：

1. 在 Spec 或 Plan 中识别决定，定位已有关联 ADR；确认是复用、原位补充、新增还是替代。
2. 在一处维护决定及理由。尚未提炼的关键方案在 Spec；提炼后以 ADR 为长期权威，Spec 保留本次应用与引用，Plan 保留执行安排。
3. 更新 ADR 状态、采纳依据、适用范围、生效条件与关系，同步索引和本次产物引用；ADR 反向链接产生它的变更及 Spec/Plan 章节。
4. 复核受影响的活跃 Spec/Plan：关键方案变化从 Spec 开始，仅执行约定变化从 Plan 开始。若发现无法维持业务承诺，交 BA 协调；实际业务依据或决定变化后修订 Intent。归档变更保留原采用版本。
5. 实现后在任务与验证记录保存真实结果，ADR 可补充证据链接；只根据实际代码与验证更新 As-Is。

本次 Spec/Plan 的应用说明、ADR 的长期决定、As-Is 的实际状态各有清楚边界，避免同一决定在多处独立改写。

## 6. 按路径加载的 Rules 与子目录说明

按路径加载适合提供局部实现约束。生成 Spec 或 Plan 时，还需按“计划影响的模块”主动读取工程规范：尚未读取源代码路径时，相应规则可能尚未进入上下文。此处不是 Intent 的输入要求。

以 Claude Code 为例，可以在 `.claude/rules/` 的 Markdown 文件中声明适用路径：

```markdown
---
paths:
  - "services/orders/**/*.ts"
  - "services/orders/**/*.tsx"
---

订单状态变更应通过项目指定的领域入口。
调整事件行为时，检查事件契约及相关测试。
```

这是语法和组织方式的示例，其中的业务规范需要替换为项目真实约定。

依据此前核验的 [Claude Code Memory 文档](https://code.claude.com/docs/en/memory)：

- 带 `paths` 的规则，在读取匹配文件时按需加载；不能假定任意 Shell 操作或路径提及都会触发。
- 不带 `paths` 的规则在启动时加载。
- 启动目录及祖先目录的 `CLAUDE.md` 在启动时读取；其下子目录中的说明随相关文件读取而加载。
- 多份说明会共同进入上下文，应主动消除矛盾和重复。

这些机制不能直接套用于其他 Agent。Codex 的 `AGENTS.md` 使用从项目根目录到工作目录的启动发现机制，具体覆盖与容量规则见 [Codex AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。跨目录或跨仓库操作时，应明确确认适用指引已被读取。

## 7. 本次变更上下文：内容、有效性与存活周期

本次变更上下文是**跨会话、跨 Agent、跨阶段保存的工作记录**。默认由三个主产物的输入依据和相关材料引用组成；较长共享事实、基线与调查索引按需抽到变更目录的 context.md。目标、方案、ADR 采用结论、任务状态和检查结果仍在各自权威位置维护，context.md 通过引用连接。

以下信息需要能够从关联记录中恢复，并不要求全部复制到 context.md：

| 内容 | 作用 |
| --- | --- |
| 变更标识、目标、范围、当前阶段 | 确定正在处理哪次变更及其边界 |
| 参与仓库及其角色 | 区分需要修改的项目与仅供参考的依赖 |
| 代码和文档版本依据 | 记录相关提交、工作区修改、Submodule 版本及 ADR 与引用材料版本 |
| 适用 ADR 与 Topic 引用 | 定位采用版本、适用范围及产物中的采用记录；Plan 关联任务和验证 |
| 已核验事实及来源 | 支撑需求理解、方案选择和任务拆分 |
| 决策、假设、待确认事项 | 避免推断被误当成事实 |
| 阶段产物、任务状态和 evidence/ 记录的引用 | 支持后续会话和 Agent 接续工作；执行下一步由 Plan 维护 |

它有三种不同的生命周期：

| 维度 | 建议规则 |
| --- | --- |
| 工作周期 | 从首次调查开始，覆盖 Intent、Spec、Plan、实现和验收，直到变更关闭 |
| 事实有效期 | 取决于相关代码、配置、需求和规范是否变化，不采用统一的固定天数 |
| 记录保留期 | 变更关闭后随阶段产物归档，按项目的记录保留约定管理 |

换会话或换 Agent 可以继续使用这份记录；暂停一段时间后，应检查相关差异再恢复。进入下一阶段、扩大影响范围或相关接口发生变化时，也应复核受影响的结论和下游产物。

ADR 的决定、条款、状态、适用范围、生效条件或替代关系变化，会影响采用它的工程上下文。先比较影响：关键方案变化时复核 Spec 和 Plan，执行细则变化时复核 Plan；保留原版本与依据。若无法继续满足业务需求，说明冲突并交 BA 协调；实际业务依据或决定变化后才修订 Intent。不能仅因 ADR 更新而自动改写需求，无关条款变化无需重做整项变更。

有效性按受影响范围说明即可。例如，订单接口发生变化，可以复核相关页面章节及 Spec 中依赖它的 Design 与 Plan 的 Tasks，无需因此重做全部调查，也不要求为每条事实建立独立状态。

变更状态可记录为“活跃 / 已归档”，默认关闭后保留原路径；有待复核内容时说明具体范围。实现期间应保留初始依据，并区分此次变更引入的新行为，避免用新现状覆盖原始决策依据。

**记录长期保留，不等于每次全部加载到模型上下文。** 各阶段只读取相关部分和必要来源。归档后的记录保留历史依据；新变更建立自己的上下文，可以引用旧记录，但需要核验其当前适用性。

Spec、Plan 阶段按 [ADR 演进规则](#adr-evolution)及时沉淀长期决定。实施收尾核对 ADR、引用材料与最终结果，补齐遗漏的决定和证据；将实际实现的可复用事实更新到 Topic As-Is。一次性调查和过程记录随变更归档，原始依据仍可定位。

## 8. 跨项目、Monorepo 与 Submodule

### 跨项目或多仓库

维护明确的项目关系与路径映射，记录每个参与仓库的职责、契约关系、本次角色和版本依据。不能仅因为目录可访问，就假定 Agent 已读取该项目的指引。

跨仓库结论应关联各自的提交或工作区状态。分支名会随提交移动，单独记录分支名不足以恢复当时的判断依据。

### Monorepo

根目录提供公共约定、系统关系和项目导航；子项目及模块维护适用的局部知识。根据影响范围选择需要读取的项目，并检查共享库及跨项目契约。

统一 Git 仓库不等于统一业务边界或统一规范。框架的项目发现机制需要单独适配。例如 Spec Kit 可以在 Monorepo 内建立独立项目，但不能据此假设各项目 Constitution 自动继承公共 Constitution。[Spec Kit Monorepo 指南](https://github.com/github/spec-kit/blob/main/docs/guides/monorepo.md)

### Submodule

Submodule 有独立仓库和历史，父仓库记录其预期提交。因此，本次上下文应同时记录父仓库版本、子模块固定版本，以及实际工作区状态。[Git Submodule 文档](https://git-scm.com/docs/gitsubmodules)

如果此次需要修改子模块，Spec 的 Design 应明确子仓库与父仓库的组合方案，Plan 的 Tasks 覆盖子仓库修改、相关验证以及父仓库引用更新；若只作参考，则按实际固定版本理解其行为。

## 9. 一次变更的推荐执行顺序

从原始诉求与 BA 材料开始、复用已有产物或恢复执行时，读取[Intent 到本地实现与验证的执行流程](../method/sdd-spec-to-commit-workflow.md)。该文档定义三个准备步骤和后续执行的动作、产出、完成条件和回退规则。

执行顺序为：Intent 明确意图并交接 BA 成果 → Spec 形成规格 → Plan 制定计划 → 按任务实现和局部验证 → 整体验证 → 审查与修正 → 必要文档同步与本地结果交接。后续 Git Commit 按实际需要接续。

各阶段继续使用本方案中的知识分层、事实核验和上下文维护方式。Git Commit 后保留变更上下文，支持后续评审和验收；变更实际关闭后再归档。

三步均形成或复用对应产物。独立小变更采用三份简短文档，部分范围开发可以复用已有 Intent 与公共方案；按设计、验收和交接需要拆分，内容深度与附件数量随实际问题调整。

## 10. 最小落地范围

建议先在一个真实项目、一项有代表性的变更上运行以下最小组合：

- 一份项目入口和统一 ADR 索引；对首批相关规范建立有来源的采用 ADR，登记范围、状态和生效条件，不要求补写全部历史。
- 简短的 Agent 入口指引，以及实际使用的 SDD 框架接入配置。
- 一项近期需求所需的 As-Is 页面，优先复用已有 Wiki；后续按实际知识缺口增加。
- Intent、Spec、Plan 的输入依据及 evidence/ 结果引用；较长共享材料按需抽出 context.md，能够定位 Design 与 Tasks。
- Spec、Plan 使用同一套 ADR 导入动作，留下采用记录，并按需产生或演进 ADR；Intent 以业务来源为依据。
- 各阶段简短的核验要求：依据是否真实、ADR 是否适用、要求是否落实、未知事项是否显式、下游产物是否仍与上游一致。

试点演练四种情况：规范通过 ADR 落到任务和验证；Spec 产生一项长期决定；Plan 发现决定变化并正确回写；旧 ADR 在新决定生效后按范围被替代，相关活跃变更得到复核。首版插件复用一套模板、索引、导入和演进规则；再按收益增加候选检索、索引生成、关系与覆盖检查。
