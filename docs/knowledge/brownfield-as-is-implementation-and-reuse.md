# Brownfield 仓库 As-Is：初始化、持续维护与复用指南

[总览与下一步](../../README.md) · 知识方法 · As-Is 的必要内容与使用方式

修订日期：2026-09-15。状态：方法草案；尚未在目标代码项目完成工具试点。

**As-Is 的目标：让 Agent 快速理解相关现状，并找到足以支撑 Spec/Plan 的仓库证据。** 默认采用一个项目入口、按需积累的知识页，以及使用前核对、变更后更新两个动作。

第一版只覆盖仓库内能够验证的现状。Intent 由 BA 根据业务来源生成并确认，As-Is 可按需帮助理解问题；完整仓库调查和工程 ADR 都不是生成 Intent 的前提。Spec 包含需求、验收条件和 Design，Plan 包含 Tasks 与验证安排，详见[三产物约定](../method/sdd-artifact-contracts.md)。

## 1. 默认范围：知识页够用，维护动作可执行

此前设计把内容要求、证据判断和未来自动化的数据结构一起放进默认流程，复杂度偏高。当前收敛如下：

| 项目 | 默认做法 |
| --- | --- |
| 内容覆盖 | 按当前问题调查；八个调查方向供查漏，不要求每页八章或逐项填写不适用 |
| 页面数量 | 从一项近期需求涉及的主题开始，缺少有复用价值的知识时再增加 |
| 结论引用 | 页面/章节链接与源码位置即可；不要求人工为每条事实编号 |
| 版本与新鲜度 | 使用现有 Git、来源链接及工具元数据；记录已知限制，使用前核对关键依据 |
| 状态管理 | 用简短文字说明未调查或待核对部分；采用工具后复用其状态，不另建一套状态字段 |
| 更新范围 | 实施者结合代码差异、页面引用和相关调用判断；不要求先建路径监控表、依赖图或影响传播服务 |
| 变更上下文 | 直接写在 Spec/Plan 的输入依据中；共享材料过长时才抽出 context.md |
| 自动化 | 优先工具原生能力；只有真实重复问题无法由配置解决时才补脚本 |

**保留对事实的要求，减少手工维护的数据结构。** 精确的测试执行证据仍按[本地执行流程](../method/sdd-spec-to-commit-workflow.md)记录；知识页通过链接使用这些证据。

## 2. 一份有用的 As-Is 包含什么

### 2.1 四个问题

| 页面需要回答 | 最小内容 | 对下一步的帮助 |
| --- | --- | --- |
| 现在做什么、怎样表现 | 能力范围、主要流程、关键规则及异常；区分已有与未实现 | Spec 确定真实变化和验收边界 |
| 在哪里、怎样实现 | 关键入口、模块协作，以及与本主题相关的数据、接口或配置条件 | Spec 的 Design 选择复用和修改位置；Plan 找到具体工作入口 |
| 有什么限制或不确定性 | 兼容要求、特殊分支、文档与代码差异、尚未调查的问题 | 避免错误方案，明确必要补查 |
| 依据在哪里、怎样验证 | 相关源码/契约/测试链接；构建和验证入口；适用版本或工具来源记录 | Agent 能核对结论，Plan 能安排实际检查 |

这些是内容问题，不是强制标题或额外四份产物。已有 Wiki 页面能够回答就直接复用。简单主题可以只有几段文字；详细字段、参数和命令清单引用仓库中的权威定义。

优先保存跨文件才能理解、经常重复调查或误解后容易返工的语义。只有目录树、函数清单和技术栈时，仍需补充代表性行为及其条件。一次性文件清单和本次任务安排留在 Spec/Plan。

### 2.2 调查方向：按问题选取

下面八个方向用于查漏，**不要求每页全部覆盖，也不把全仓调查作为开始开发的条件**：

| 方向 | 何时深入 |
| --- | --- |
| 能力、术语与边界 | 无法判断需求属于哪个能力，或系统责任不清 |
| 当前行为与规则 | 需要确认状态、权限、异常、重复操作和回归边界 |
| 实现结构与关键流程 | 需要选修改入口、复用模块，或理解同步/异步协作 |
| 数据语义与生命周期 | 涉及字段含义、状态迁移、持久化、删除或一致性 |
| 接口与集成契约 | 涉及 API、事件、外部系统、生产者或消费者变化 |
| 配置与共享机制 | 行为受鉴权、事务、重试、缓存、并发或运行配置影响 |
| 约束、决策与例外 | 存在兼容要求、特殊分支、历史原因或文档冲突 |
| 开发与验证路径 | 需要确定测试位置、环境、数据准备及执行命令 |

结束调查的依据是：当前 Spec/Plan 的关键判断已有依据，剩余未知项的影响清楚。页面没有涉及无关方向时无需解释；与当前判断有关但未查清的内容要明确写出。

### 2.3 证据规则

- **实现事实：** 结论链接到相关仓库路径、符号或契约；重要行为检查前置条件和关联分支。行号可辅助定位。
- **文档与决定：** README、ADR 或目标规格表达声明和决定，需核对实际实现；ADR 已接受不表示代码已经完成。
- **测试与结果：** 测试代码表达预期。只有实际运行后，才能引用该代码状态、环境和场景下的结果。
- **推断与未知：** 不能从仓库确认的生产配置、外部系统内部行为和业务原因如实标明。未找到实现，只能说明已查范围内未发现。
- **版本：** 页面或工具元数据应能定位调查所依据的代码状态。采用 Git 管理的 Wiki 可复用文档修订及关联源码版本，不要求逐页手填 hash。

使用未提交实现时，应说明相关工作区变化，不能写成默认分支或已部署事实。工具已经保留来源内容标识时直接复用；确需复现某次未提交证据而现有记录不足时，再保存相关差异或快照。历史来源无法恢复时，重新核对本次关键依据，不补造版本。

来源未变、链接可解析或页面被工具标为 verified，均不能单独证明语义正确、调查完整或实际测试通过。关键判断在使用时仍需结合相关实现核对。

## 3. 第一次初始化

**输入：** 目标仓库、已有项目指引和文档、近期需求（如有）。已有资料先复用；没有明确需求时，从主要能力选一个值得反复使用的主题。

| 动作 | 具体做什么 | 完成条件 |
| --- | --- | --- |
| 1. 建入口 | 确认仓库范围和代码状态，链接已有模块说明、知识页、ADR、构建及测试入口 | Agent 能从业务概念找到调查起点；未知范围清楚 |
| 2. 补相关知识 | 选择近期需求涉及的能力，沿代表性入口追踪规则、数据变化和相关调用；补写四个问题的答案 | 关键结论有来源，与本次判断有关的未知项已标明 |
| 3. 试用和修正 | 用该需求形成或评审 Spec/Plan，观察还需要重复查什么 | 能确定变化、方案落点和验证路径；高价值缺口回写知识页 |

可用普通搜索、直接读代码、已有 Codegraph，或候选 Wiki 工具完成这些动作。知识工具生成了更多页面时按原生导航使用；优先核对本次相关页面，不要求逐页审完才能开始工作。

**输出：** 现有项目入口的补充、相关知识页，以及必要的调查限制。实际运行检查才产生检查记录；简短调查说明可留在页面或本次主产物中，无需额外生成一套初始化报告。

## 4. 各步骤如何读取

| 步骤 | 输入方式 | 需要形成的结果 |
| --- | --- | --- |
| Intent | BA 以业务诉求、规则、方案/原型和确认材料为主；按需参考已有现状 | 业务目标与范围。技术未知可以交 Spec；不导入工程 ADR 作为需求准入条件 |
| Spec | 从项目入口找到相关知识页，读取适用 ADR，再核对影响需求、AC 和 Design 的源码、契约与条件 | 明确当前与目标变化、方案落点、重要影响及未决问题 |
| Plan | 复用 Spec 的依据，深入本次文件、测试布局、依赖和环境条件 | Tasks 能执行，验证方式和必要准备明确 |
| 实施/恢复 | 读取当前 Spec/Plan 和实际工作区，检查相关输入是否变化 | 有效内容继续复用，变化影响记录回相应产物 |

读取顺序：**入口定位 → 相关页面 → 决定本次判断的源码与 ADR → 缺口补查**。不把整库 Wiki 全部加载进每一步。

在 Spec/Plan 的“输入依据”中记录采用的页面或章节、必要的版本/补查来源，以及仍有影响的未知项。共有依据引用上一步；无需重复摘抄整页，也无需建立“事实 ID → AC → Task → 测试”的追踪表。

Wiki 内容过期不必阻塞整个开发流程：先从当前代码核对本次需要的部分，继续有依据的工作；有长期价值的修正回写原页面。若依赖某个未解决事实才能设计或实施，只暂停该部分。

## 5. 持续维护：两个日常时机

### 5.1 使用前核对

生成 Spec/Plan 或恢复任务时，结合工具来源状态与 Git 差异判断哪些页面可能受影响，再直接核对当前决策依赖的实现。新增入口、配置装配、共享依赖和消费者变化也可能改变旧结论，不能只看页面已引用的文件。

代码状态包括本次实际使用的提交、暂存/未暂存修改及未跟踪文件。源文件未命中变化列表不证明没有影响；代码索引可能需要同步。没有可靠旧基线时，直接重新核对相关范围。

### 5.2 代码改完后回写

实施者在本地交接时回答：**这次改变了哪些可复用的现状，哪些页面需要更新？**

| 变化 | 处理 |
| --- | --- |
| 行为、接口、数据或重要配置条件改变 | 更新相关页面中的结论与来源，检查相邻流程和消费者 |
| 新增、删除或替代能力 | 调整知识导航与相关说明 |
| 重构后结论仍成立 | 必要时修复来源定位，保留准确的正文 |
| 只影响本次实施细节 | 记录在 Spec/Plan 或检查证据中；没有知识变化可简记“无需更新” |
| 尚未核实或更新未完成 | 明确受影响部分及下一步；当前交付依赖的事实需直接核实 |

复用工具的 update 与来源检查，核对生成的差异后采用。未实现的目标继续留在 Spec；本地已实现行为按对应工作区版本描述，之后可与代码一同提交。

**完成条件按本次步骤记录：** 相关知识已更新、复核后无需改正文，或具体缺口已说明。无需为每条事实另建处理记录。事实变化确实影响活跃 Spec/Plan 时修订相应部分；只有业务来源或决定发生变化才由 BA 修改 Intent。历史记录保留当时依据。

定期全库刷新、自动影响传播、Git hooks 和逐事实状态图都不是首版前提。出现经常漏更或过期页面后，再选择现有工具补相应机制。Git hooks 只适合快速、确定性的检查，不在提交过程中运行完整 Wiki 生成。

## 6. 工具分工与复用

### 6.1 若采用 OpenWiki

OpenWiki 是知识维护候选，当前并未选定或完成目标项目试用。源码能力与限制见[知识工具研究](../../research/tools/tool-reuse-knowledge.md)，完整适配分析见[工具选型页](../tools/existing-tools-reuse-plan.md#3-openwiki知识维护候选的适配分析)。

| 职责 | 采用时的安排 |
| --- | --- |
| Wiki 页面、导航、来源关联和更新运行 | 优先使用 OpenWiki 原生能力及元数据 |
| 本项目需要哪些知识 | 在 `openwiki/INSTRUCTIONS.md` 写简短内容指引，按需求补行为、数据、契约和未知项 |
| Spec/Plan 如何使用 | 项目指引约定按范围读取，核对关键源码及适用 ADR，引用有效依据 |
| 何时维护 | 使用前检查相关页面，实施收尾触发需要的 update，并审阅更新结果 |
| 实际测试与交付结论 | 沿用项目检查和步骤证据；Wiki 的内部校验不承担此职责 |

OpenWiki 的内置指令已覆盖行为、跨组件流程、状态、异常、配置和测试等调查方向，[源码依据](../../research/tools/tool-reuse-knowledge.md#2-openwiki-能直接承接什么)见研究笔记。它能承接知识生产与维护的工具工作；生成内容是否足以支撑本项目方案仍须试用核验。**增加 OpenWiki 后，先补项目调查重点和流程接入，通常无需另建 As-Is 管理程序。**

### 6.2 保持一份正文

- 项目入口优先复用既有位置，缺少时采用 `docs/project/README.md`，连接知识、ADR 与执行流程。
- 普通 Markdown 知识页默认放 `docs/knowledge/topics/<slug>.md`。Topic 只是“主题知识页”的称呼，不要求专门实体或编号系统。
- 采用 OpenWiki 时，正文留在原生 `openwiki/`，项目入口链接 `openwiki/index.md`，不复制到默认 Topic 目录。
- 来源、指纹、页面运行状态已有工具管理时直接使用，不再手工镜像成另一套 YAML、事实编号或状态表。
- ADR、Intent/Spec/Plan 和实际检查记录继续保留各自权威位置，详见[统一文档体系](../method/project-documentation-system.md)。

### 6.3 跨项目与复杂仓库

复用内容指引、读取规则、收尾动作和工具配置；项目事实、路径及验证结果重新调查。换 Agent 只需它能找到这些入口并读取当前产物，不要求特定宿主机制。

多仓库结论注明各自来源与版本，外部服务只描述已检查的一侧。Monorepo 的共享模块变化需要看实际消费者；Submodule 核对父仓库引用与子仓库实际状态。工具对这些结构的支持分别验证，出现跨仓库需求再增加协调索引，不预先自建统一图谱。

## 7. 可复制的最小模板

已有 Wiki 或项目说明内容足够时直接复用，不要求迁移为同一格式。

### 7.1 项目入口

```markdown
# 项目入口

- 职责与术语：<简述或已有文档>
- 能力与实现导航：<知识索引、主要入口；未调查部分>
- 工程依据：<ADR、契约位置>
- 开发与验证：<环境、构建和测试说明>
- 工作方式：<Intent/Spec/Plan 位置；按需读取和收尾更新约定>
```

### 7.2 知识页

```markdown
# <能力/主题>

范围：<描述哪部分，已知未覆盖什么>
依据：<仓库版本/文档修订或工具来源记录；有未提交实现时说明>

## 当前行为
<主要场景、规则、关键异常；在对应结论处附源码链接>

## 实现入口与协作
<模块/路径/符号；按需说明相关数据、接口、配置和调用关系>

## 限制与未知
<重要例外、文档冲突、未查清且会影响决策的问题>

## 验证入口
<相关测试、环境与命令的权威位置；已执行结果链接，无结果时不声称通过>
```

采用 OpenWiki 时将这些内容要求写进指引，允许生成器使用适合项目的页面结构。来源与版本已有工具记录时引用即可，模板不是另建元数据的要求。

### 7.3 Spec/Plan 中的输入依据

```markdown
## 输入依据

- 相关现状：<知识页/章节，以及本次补查的重要源码位置>
- 工程约定：<适用 ADR 及其原文位置；共用依据可引用 Spec>
- 当前适用性：<相关代码状态与必要核对；只记影响本次判断的差异>
- 未解决项：<影响、处理方式和下一步；没有则省略>
```

只有跨阶段共享材料过长时才抽成 context.md。任务和完成状态留在 Plan，实际检查结果留在 evidence/，输入依据通过链接使用。

## 8. 三段可复用指令

**初始化：**

```text
为 <目标仓库> 建立足以支持 <近期需求> 的 As-Is。
先读项目指引和已有文档，补齐项目导航；优先复用已有知识。
围绕相关能力说明当前行为、实现协作、限制/未知和验证入口，重要结论附仓库来源。
仅描述查证到的现状。用该需求检查知识能否支持 Spec 的变化/方案和 Plan 的执行/验证。
输出文档位置及影响下一步的缺口；有工具时沿用其原生知识目录和来源记录。
```

**生成 Spec/Plan 时读取：**

```text
依据 <项目入口> 为 <本次需求> 准备 <Spec/Plan>。
先选相关知识页和适用 ADR，再核对影响本步判断的源码、契约及工作区变化。
针对重要未知项补查，将有效引用和剩余问题写入本步产物，按授权继续工作。
已有页面过期时核实本次所需部分，并将可复用的修正回写原页面。
```

**实施收尾或恢复时维护：**

```text
结合 <当前 Spec/Plan>、实际代码差异和检查结果，判断哪些 As-Is 页面受影响。
检查相关新文件、配置和消费者；需要时调用知识工具的更新能力并核对输出。
将实际实现与来源更新到唯一正文，说明本步骤的更新结果或无需更新的理由。
有未解决问题时写明范围和下一步；恢复任务时在关键依据有效的范围内继续。
```

## 9. 下一步：一个主题、一次变更的对照试点

在统一选型中，将 OpenWiki 作为候选与现有 Codegraph/搜索/直接读取方式比较。无须先把整套文档规范做成插件或新增脚本。

1. **同一输入：** 选一个真实仓库、一项需求和相关主题，保持代码版本、模型及调查任务尽量一致。
2. **看内容：** 能否说明当前行为和重要条件；关键结论是否有正确来源；是否把未知、决定和实现分清。
3. **看消费：** 用知识形成 Spec/Plan，检查方案是否选到真实入口、是否漏掉重要依赖、验证是否可执行，并记录仍需补查什么。
4. **看维护：** 做一次相关小改动，包含新文件或共享机制影响时一并观察；执行更新，检查知识是否一致、是否大面积无关改写、失败是否能接续。
5. **看成本：** 记录首次生成、审阅修正和后续更新的时间、模型用量及配置负担，对比减少的重复调查。

只在这个案例中，知识有助于正确完成 Spec/Plan 且维护成本可接受，才有依据把候选纳入组合；不能据此宣称其他语言、规模或仓库结构已经适配。通过后把可复用的内容指引、读取规则和收尾动作纳入插件，更多自动化由实际缺口决定。
