# AI SDLC 实现分工：Skill、脚本、Agent 机制与 Git hooks

[总览与下一步](../../README.md) · 选型与实施参考 · 候选未定，自研按实测缺口决定

更新日期：2026-09-16。本文定义现有流程如何实现，属于方法层设计；尚未创建技能、脚本或 hooks。准备阶段沿用 Intent → Spec → Plan；当前执行终点是本地代码生成、验证、审查与结果交接。步骤和完成条件见[执行流程](../method/sdd-spec-to-commit-workflow.md)，产物职责见[产物约定](../method/sdd-artifact-contracts.md)。

实现时先按[已有工具选型与复用路线](existing-tools-reuse-plan.md)广泛调研、统一筛选并实测，再确定工具组合。本文的能力分组是职责划分，不是必须自研的模块清单。默认采用[步骤级记录](../method/sdd-artifact-contracts.md#granularity)，不要求逐项 AC/Task/测试/运行结果映射；现成配置与已有报告足够时无需补脚本。

## 1. 四类机制怎样组合

**Skill 写方法，Agent 执行推理和协作，脚本执行确定性操作，Git hooks 在 Git 事件上调用脚本。** 一项能力通常由其中几类共同组成。

| 机制 | 负责什么 | 承诺的边界 |
| --- | --- | --- |
| Skill | 可复用的触发说明、输入读取、动作顺序、判断要求、输出位置与交接规则 | 是给 Agent 的操作指引；自身不提供进程隔离、强制权限或可靠的确定性检查 |
| 脚本/已有 CLI | 读取状态、解析约定字段、检查关系、执行测试、规范化结果和受控写入 | 对明确输入执行可重复操作；结构完整、命令成功不证明需求或方案正确 |
| Agent 机制 | 根据证据推理、调用技能和工具、维持局部反馈循环、隔离上下文、分派和接续工作 | 能力依赖宿主；独立上下文要实际创建，角色名称本身不构成隔离 |
| Git hooks | 在指定 Git 操作前后触发小范围脚本 | 是事件入口；不能覆盖尚未触发 Git 操作的本地实施与验证 |

例如 Spec 由 Agent 按 Skill 读取 Intent、ADR 与 As-Is 并形成方案；脚本检查引用、结构和 ID；需要时交给独立 Agent 审查。后续 pre-commit 可以再次调用同一检查脚本。四者服务于同一份 spec.md，不各自产生一份规格。

Git hooks 与部分宿主提供的 Agent 生命周期 hooks 分属两种事件机制。后者如会话、工具调用或停止事件，只能在选定宿主后适配；当前通用流程不依赖这些事件保证状态正确。Agent 停止也不等于 Task 完成。

## 2. 按整体流程分工

下表描述职责，既有工具能完成的工作直接复用。Git hooks 列均为后续可选接入；首版通过 Agent 显式调用脚本运行同样的检查。

| 流程/能力 | Skill 中定义什么 | 脚本或已有工具做什么 | Agent 机制做什么 | Git hooks 的位置 |
| --- | --- | --- | --- | --- |
| 项目与工具初始化 | 发现、复用、缺口处理、路径映射与实际能力检查 | 读取布局/配置/版本；生成缺少的受管理骨架；核验可用命令 | 判断工具用途和项目适配；已有授权内补齐条件 | 后续安装 hook 时检测现有管理方式；核心初始化不依赖 hook |
| Brownfield As-Is 初始化/调查 | 调查范围、事实与推断区分、证据和 Topic 内容要求 | 文件/符号检索、代码图查询、来源定位、基线与链接检查 | 阅读代码并解释行为，判断覆盖及未知项 | 不在 hook 内调查或生成现状 |
| Intent | BA 材料读取、目标/范围澄清、设计采用、BA 确认与交接规则 | 复用文档/原型读取工具和模板；按需检查字段与链接，保留访问缺口 | 辅助 BA 起草和修订，核对实际确认依据；业务表述由 BA 确认，越权取舍交现有决策人 | 后续仅检查受管理文档的结构和链接 |
| Spec（含 Design） | ADR/As-Is 读取、需求与 AC、方案取舍、交接条件 | 检查产物结构、引用及 ADR 状态线索 | 核验事实、设计方案、判断 ADR 适用性；按需独立审查 | 不在 hook 内生成/采纳方案或 ADR |
| Plan（含 Tasks） | 文件落点、工作拆分、检查安排、依赖与完成条件 | 检查产物输入、引用和路径；明确采用结构化任务依赖时再校验 ID 与循环 | 判断粒度、先后关系、检查是否足够、前提是否可执行 | 后续可复用已有结构检查；不替代语义审查 |
| 执行准备/恢复 | 输入核对、已有修改归属、环境和受阻范围 | 读取实际工作区（含新增文件）、输入变化和可用命令，定位已有结果 | 主 Agent 根据证据选择可执行 Task 和接续点 | 每次恢复仍显式核对；post-* 只能提供变化提示 |
| Task 实施闭环 | 读取要求、建立检查、实施、诊断、修正和停止规则 | 运行仓库既有工具与检查，记录修改状态和实际结果 | 执行节点生成代码；主 Agent 路由局部修正、上游修订或等待 | 不用 hook 驱动代码生成或重试循环 |
| 变更验证 | 检查选择、组合行为、证据范围、失败归因与结果复用 | 执行命令/操作，保存受检状态、退出状态和报告；核验结果引用 | 判断检查充分性、外部限制、影响范围及是否需补验 | 后续 pre-commit/pre-push 调用已选定的有限检查集 |
| 审查与修正 | 原文读取、审查维度、发现证据、处理与复查规则 | 收集完整差异，检查受审版本是否变化，复跑受影响检查 | 独立上下文判断遗漏和正确性；执行者处理有效发现 | 不在 hook 内启动 LLM 审查或自动修复 |
| ADR 演进 | 采用、例外、补充、替代及授权规则；嵌入 Spec/Plan | 检查 ID、状态字段、替代关系、索引与来源引用 | 判断决定性质及影响，按已有权限采纳或转交 | 只校验关系，不因提交事件自动采纳/替代决定 |
| 文档/As-Is 增量维护 | 受影响范围、实际事实、回写与未知项规则 | 根据差异与引用找候选、检查链接/基线，生成派生索引 | 阅读新证据，判断需更新哪些结论和具体内容 | post-* 可提示索引待核对；不直接改事实正文 |
| 本地结果交接 | 本地完成条件、剩余事项及下一步 | 汇集版本与结果引用，核对受检状态，受控写入 Plan | 判断本次完成范围，避免把部分结果当成整体完成 | 本地完成不要求触发任何 Git hook |
| 后续本地提交 | 提交范围、证据适用性和结果核对 | 检查暂存快照、提交约定及实际结果 | 按已有授权组织提交与处理失败 | pre-commit、commit-msg；push 接入后才考虑 pre-push |

## 3. Skill：按可复用任务组织入口

建议首版保留以下七个逻辑入口。名称用于设计讨论，宿主命令与发布名称尚未确定。

| 入口 | 使用场景 | 默认输出/复用方式 |
| --- | --- | --- |
| 项目准备 | 初次接入或诊断项目文档与工具条件 | 项目入口和路径映射；实际检测证据；保留已有配置 |
| As-Is | 首次整理、按变更调查、核验并更新相关 Topic | 有来源的事实与未知项；可被 Spec/Plan/执行流程调用 |
| Intent | 从业务诉求、BA 分析/方案/原型及澄清生成或修订交接稿 | intent.md；已有完整成果通过引用复用 |
| Spec | 从 Intent 与项目依据形成要求与方案 | spec.md；按需演进 ADR |
| Plan | 从 Spec 形成可执行工作 | plan.md；任务、验证安排与状态 |
| 执行/接续 Plan | 本地实施、组合验证、修正、恢复和结果交接 | 代码及配套改动、Plan 状态、实际证据；调用共用验证与维护方法 |
| 审查 | 独立审查，或对已有变更进行指定范围的审查 | review.md 中的可定位发现；明确自查或独立方式 |

验证、ADR 维护、上下文读取、本地交接先作为上述入口共用的工作流章节和脚本能力。出现稳定的独立使用需求后再增加独立 Skill。一个 Skill 可以被主 Agent 或子 Agent 使用；一次步骤也可以组合多个 Skill，不按每个流程框或文档各建一套入口。

每份 Skill 只保留：触发与边界、必要输入及读取顺序、推理和动作要求、脚本调用约定、输出位置、完成/返回/等待条件。详细模板和规则通过明确指针读取，避免把 ADR 原文、共享规则或整份方法文档复制进每个 Skill。

Intent 首先用现有宿主、材料读取能力、Skill 指引与模板演练；无需预设独立 BA Agent 或专用脚本。原型只能读取图片时说明可见范围，不能宣称检查过交互或隐藏状态。生成步骤与 BA 交接条件以 [Intent 约定](../method/sdd-artifact-contracts.md#intent)为准；只有实测发现重复的格式转换或读取缺口，才评估补工具。

ADR 导入放在 Spec/Plan 和实现入口，Intent 不运行工程 ADR 的符合性检查。Spec 发现需求与历史决定冲突时说明方案和代价，按已有权限处理工程约定；业务承诺需要改变时交 BA 协调，不能由工具自动降低需求。

三个入口都先识别本次业务目标与开发范围，定位有效产物，再决定复用或补充。Skill 负责确认依据读取、共享材料选择、按需拆分和变化检查；Agent 据此处理已授权范围。启动 Intent 可从原始需求开始，Spec/Plan 仍需各自约定的完整输入；所有入口均不要求 Feature/Story 分类，该信息只作可选外部关联。脚本按需检查结构和引用，不据标签批量生成文档；Git hooks 不负责业务确认、需求拆分或完成判断。

<a id="policy-application"></a>

### 3.1 规则如何进入执行并持续改进

工程规则的权威内容仍由 ADR 及其明确采用的来源维护。Skill、宿主指引和检查配置承接执行方式；重复使用的规则通过引用或受管理的派生配置加载，不独立维护第二份政策正文。

| 环节 | 责任与内容 | 最小可核查结果 |
| --- | --- | --- |
| 确认采用 | 既有规则负责人确认内容和适用范围；项目工程负责人在权限内决定本项目的工程采用，沿用 ADR 接受规则 | 来源、修订、有效状态及本次适用范围 |
| 配置执行 | 工程负责人或其委托的维护者，把适用规则接入已选择的 Skill/指引、工具检查或审查方法 | 规则来源与执行入口、配置版本的关联；没有自动执行能力时如实注明 |
| 验证触发 | 用应触发、不应触发及实际违规的代表性案例核对执行方式 | 实际读取和检查结果；仅安装 Skill 不证明它被应用 |
| 处理更新 | 来源语义或适用范围改变时，比较采用记录和受影响配置；正文变化与工具实现变化分别核验 | 需要更新的配置、活跃工作及回归案例；历史结果保留原版本 |
| 反馈改进 | 审查发现或实际失败先判断来自漏读、歧义、未触发、检查不足还是实现错误，再交相应维护者 | 在既有规则、配置或案例中修正，后续验证是否仍重现 |

组织规则例外仍由有权的规则负责人处理，工具维护者不能通过修改 Skill 消除有效硬约束。尚无插件的本地试点，可以通过明确读取来源和执行既有检查验证同一规则；只有存在重复、稳定的执行需要时才固化专用 Skill 或配置。

运行证据按需引用实际采用的规则与配置版本，触发验证和维护结果写入既有项目活动证据或本次变更 evidence；不增加规则台账。配置变化的采用条件由产品回归约定承接，不能用一次触发成功代替整体效果判断。

模型、提示词、Skill、规则映射、权限或宿主配置变化，按[配置回归与采用](../roadmap/ai-sdlc-plugin-roadmap.md#configuration-evaluation)选择受影响案例；质量满足要求且没有已知退化后才比较速度与成本。

## 4. 脚本与 CLI：复用的能力与按需缺口

已有 Git、搜索、构建、测试、格式及类型检查工具优先复用。下表用于检查已有能力和潜在缺口，不预设四组自研模块。初期用步骤产物、工作清单、配置和原生报告演练；反复出现且现有配置无法解决的问题再编写薄封装。

| 能力组 | 输入 | 输出 | 脚本不得自行作出的判断 |
| --- | --- | --- | --- |
| 项目与状态检查 | 项目路径映射、仓库/文件范围、上次输入基线 | 当前布局、工具信息、HEAD（若有）、相关已修改/暂存/未跟踪文件与内容标识、变化候选 | 某项变化是否改变业务语义，某 Topic 是否已经过期 |
| 产物与引用检查 | 受管理文档、被引用的步骤产物与来源 | 缺失文件、失效引用、无法解析项；项目另有结构化依赖时再检查 ID 和循环 | 方案是否合理、AC 是否足够、ADR 是否已获得采纳权限 |
| 验证执行与记录 | 已选定的命令/参数、工作目录、必要环境、检查范围和预期判据 | 原生实际输出/报告、受检状态和步骤结论；必要时沿用工具运行标识 | 退出码为零是否证明所有 AC 完成，Mock 结果能否代表真实外部集成 |
| 受控产物写入 | 目标文件、期望修订、已形成的内容或状态更新、依据引用 | 骨架、增量更新或实际结果追加；当前版本不符时报告冲突 | 自动接受 ADR、替用户改变范围、凭字段齐全宣告语义完成 |

实现要求：

- **默认检查与修复分开。** 检查返回问题；生成骨架、修复格式、更新正文等写入由明确动作调用。保留已有内容，避免自动重写整个文档。
- **写入前核对当前内容。** 内容已有相关修改时先重新读取并协调，首次创建不覆盖同名文件。仅在自动追加、多次恢复或并发写入确有需要时增加修订检查和去重机制。
- **保留真实结果。** 执行失败、超时、未执行与实际检查不通过可辨认；未知格式返回无法判断，不能默认为通过。是否满足验收仍依据检查判据及实际证据。
- **区分受检对象。** 工作区、暂存快照和某个提交分别标明。新文件纳入本地验证；记录所用的源码、测试、配置、输入和环境条件。
- **生成派生数据。** 索引或状态摘要引用正文，不能成为另一套可独立修改的任务/决定来源。脚本可以校验状态更新的必要字段和证据引用，但不能单凭引用存在判断任务正确完成。
- **限制检查范围。** 按项目采用的模板和本次影响运行；未纳管的历史材料不因缺少新模板字段被一律判错。

M0 用现有命令和步骤记录演练。M1 只固化已证实重复且易错、工具配置又无法解决的操作；M2 按实际收益增加维护与并发支持。不存在实际缺口时可以没有自研 runtime。

已有工具对应关系：

- OpenWiki 已提供 Wiki 来源版本检查、Claim 维护和逐页恢复，知识维护先验证这些实现；不另写一套相同存储。
- OpenSpec 可复用产物 schema 和依赖检查；Spec Kit 的 preset/workflow 是替换方案。它们的产物依赖不同于 Plan 的业务 Task 依赖，完成提示也需映射。
- markdownlint-cli2、lychee 和按需选取的 check-jsonschema/Ajv 可承担通用检查；本项目只补选定组合实际暴露的步骤交接或记录缺口。
- 项目既有测试与报告继续复用；mise 和 hook 管理器按缺口选择。具体默认行为和版本见[确定性工具研究](../../research/tools/tool-reuse-validation.md)。

## 5. Agent 机制：先可靠运行，再按收益拆分

| 机制 | 使用位置 | 首版约定 |
| --- | --- | --- |
| 主 Agent 协调 | 各步交接、执行 Plan、接续、失败路由 | 兼任协调职责；统一维护 Plan，读取脚本结果后判断下一动作 |
| 单任务反馈循环 | 调查、生成和 Task 实施 | 有目标、检查、修正与停止条件；不把循环计数当进度 |
| 独立上下文 | 需要独立判断的审查 | 实际创建新会话或宿主支持的独立 Agent；重新读取必要原文、代码和证据。只切换角色提示不算隔离 |
| 子 Agent 分派/汇合 | 独立审查；后续多个独立调查范围 | 先试点执行与审查；只有工作可分离且收益明确时才并行，列明预期分支和汇合条件 |
| 恢复和运行状态 | 中断、输入改变或换会话 | 用 Plan 和证据恢复；宿主 checkpoint 作为恢复指针，任务权威状态仍在 Plan |
| 文件与工具范围 | 多个节点协作或执行仓库工具 | 在指引中明确读写范围，采用宿主实际可提供的权限和隔离；不把 Skill 文本视为强制权限机制 |

首版可由主 Agent 自行实施并调用工具，再用独立审查者检查；也可将明确 Task 交给执行子 Agent。两种方式复用相同输入输出。审查节点可交回原执行节点继续修正，无需每次重新创建执行者。

并行不是流程前提。需要并行修改时再采用合适的工作区隔离和写入协调；隔离工作区也不能消除共享接口冲突，汇合后仍需组合验证。独立审查不可用时明确记录实际方式，不把自查写成独立审查，也不越过项目要求。

<a id="action-controls"></a>

### 5.1 必要动作限制、能力核验与降级

每次执行只核对本次范围实际需要的控制，不把所有企业级控制都设为本地 MVP 的前提。工程负责人确认项目要求的受保护动作及适用范围，宿主或工具维护者提供实际执行机制；声明已有授权不能代替机制有效性。

| 核对项 | 最小内容 |
| --- | --- |
| 受保护对象与动作 | 项目明确限制的文件、系统、环境或操作，以及限制依据 |
| 执行机制 | 实际生效的宿主权限、文件/网络隔离、工具授权、服务端或流水线条件；Skill 文字只作行为指引 |
| 能力证据 | 在隔离或无副作用场景核对允许与拒绝的结果；记录实际版本和适用边界，不能仅凭配置文件存在判定有效 |
| 不满足时的处理 | 替代隔离方式、可继续范围、受阻动作、解除条件及接收人 |

**按受影响动作降级。** 必要限制不可用时，先使用已有且能核验的隔离或权限机制满足同一要求；仍无法满足，就对该动作转为只读分析、在允许位置形成建议或补丁，交给具备条件的执行者。其他已授权且条件具备的工作继续；依赖受阻结果的后续工作保持受阻。

降级不能绕过本来受限的访问或写入，也不能把事后审查当作执行前限制的替代。恢复时重新核对控制是否已生效、输入和授权是否仍适用，不因重新启动会话而自动解除限制。控制的实际检查结果写入既有 verification 或项目活动证据，Plan 引用可继续和受阻范围。

团队交付时还需核验代码负责人批准及发布授权的实际执行条件，见[团队交付与发布](../method/sdd-spec-to-commit-workflow.md#team-delivery)。本地 Git hooks 继续保持可选，不因此承担全部动作权限保证。

缺陷修复中，受保护的复现检查按[测试保护与更正](../method/sdd-spec-to-commit-workflow.md#reproduction-test-correction)处理：有效判据不能被修复者削弱；确有错误时经授权复核后更正，再恢复相应验证。只对需要保护的检查范围设置限制，不锁死正常功能开发的全部测试。

<a id="hooks"></a>

## 6. Git hooks：可选的 Git 事件适配

Git hook 的触发和退出语义以[Git 官方文档](https://git-scm.com/docs/githooks)为准；核验细节见[来源记录](../../research/execution/git-hooks-sdlc-boundaries.md)。下面的使用安排是本项目建议。

| Hook | 建议承接的操作 | 引入时机 |
| --- | --- | --- |
| pre-commit | 对拟提交内容运行快速格式/结构/引用检查；项目已要求的小范围测试 | 接入本地提交后 |
| commit-msg | 已采用的提交消息格式检查 | 项目有明确提交约定时 |
| pre-push | 项目认可的较重验证或结果适用性检查；注明实际验证的引用/快照范围 | 后续接入 push 后 |
| post-checkout | 标记可重建的索引或缓存需要重新核对 | 分支切换导致重复维护成本时 |
| post-merge / post-rewrite | 提供索引、缓存或已有结果的复核线索 | 增量维护工具成熟后 |

实施边界：

1. **核心检查有直接入口。** Agent 执行、手动验证、后续 hooks 和 CI 可调用同一检查实现，按各自范围运行。没有触发提交，也能完成本地验证。
2. **校验真实的拟提交内容。** 部分暂存时，工作区检查通过不能证明暂存快照通过。支持读取索引的检查应读取索引；需要文件树的检查应在可复核的候选快照中运行。尚不支持时明确该限制并返回处理要求，不静默拿工作区代替；不通过自动 stash/reset 隐藏这一差异。
3. **Hook 保持短小、可解释。** 只选择项目约定且执行成本合适的检查；不启动 LLM、不生成 Spec/ADR/As-Is、不自动修复再提交、不在其中组织 Agent 闭环。正文变化由正常维护流程处理。
4. **复用现有安装方式。** 检查现有 hooksPath、hook 管理器及脚本；经项目选择接入后组合已有逻辑，不覆盖现有 hooks 或更改全局配置。放进版本库的脚本仍需要被正确安装或配置才会执行。
5. **事件提示需要再次核验。** Git hooks 不监听普通编辑器修改，post-* 也不能作为完整变更监听器。执行/恢复入口仍比较实际状态；提示只影响可重建缓存，不直接把 ADR、As-Is 或任务标成失效或完成。
6. **不把本地 Hook 当作强制保证。** 某些 hooks 可跳过或禁用；成功只证明相应检查在其范围内完成。团队需要强制检查时，后续接入服务端或 CI 等可验证的执行条件，仍不把它们当作语义审查的替代。

当前范围到本地实现与验证，因此 M1 的完成条件不依赖安装 Git hooks。已有项目 hooks 继续按项目规则运行；后续新增适配遵循上述分工。

### 6.1 MR 事件与 Colla MCP 的后续接入

MR 收尾的目标行为由[执行流程第 9.5 节](../method/sdd-spec-to-commit-workflow.md#mr-closeout)维护。代码托管平台的事件通知或流水线负责唤起处理；已有 API/CLI 核对实际 MR 与分支状态；Colla MCP 按已授权字段同步正文或进度。具体能力需要在选定平台与 MCP 上验证，本文不预设某个厂商接口，也不将 MCP 可调用视为有权关闭事项。

先用现有事件入口、权限、任务串行化和条件更新机制实现；确有重复缺口时再补薄连接代码。核验事件来源、项目/范围映射、重复与乱序通知、并发收尾、部分写回成功和中断恢复。事件入口不自行决定业务验收或扩大生产操作权限，复杂判断仍读取有效产物与实际证据。无事件机制时，已授权执行者也可手动调用同一收尾流程，核验规则保持一致。

## 7. 实现资产与项目产物放在哪里

以下为未来方法包的逻辑目录，尚未创建。详细内容各有一处来源，宿主包装只做映射。

```text
workflows/              # 步骤、读取、判断、返回和维护规则
contracts/              # 产物、脚本输入输出、节点交接约定
templates/              # 文档与结果记录骨架
skills/                 # 可复用入口及指向上述规则的说明
runtime/                # 状态检查、关系校验、执行记录、受控写入
adapters/agents/        # 宿主会话/子 Agent/上下文与工具调用映射
adapters/git-hooks/     # 可选薄入口，调用 runtime 或项目已有命令
evals/                  # 行为、遗漏、失败、恢复与接口场景
packaging/              # 选定宿主后的安装包
```

运行结果继续遵循[统一文档体系](../method/project-documentation-system.md)：Intent/Spec/Plan、ADR、As-Is、代码与 evidence 留在项目中。Skill 或 hooks 安装目录不保存项目的权威任务状态。Git hooks 的实际启用位置由项目已有安装方式决定，不要求复制到特定宿主插件目录。

## 8. 首版顺序与验收

1. **M0：稳定约定和复用试点。** 完成候选筛选后，用三步产物、步骤交接及本地完成条件演练入围组合，明确已有覆盖与实际缺口。
2. **M1：完成本地路径。** 改编可复用 Skill，补必要适配脚本，先运行单 Task 闭环，再验证独立审查和恢复；同一个检查入口可由 Agent 或开发者调用。
3. **M2：形成可复用包装。** 按试点需要增加宿主包装、工具版本兼容、日常知识维护及提交 hooks；并行、push 和远端集成按后续范围接入。

验收分别检查：Skill 能否使不同会话读到正确输入；脚本能否如实报告缺失、失败和版本冲突；Agent 是否基于证据修正和接续；后续 hooks 是否检查正确快照、保留既有配置，并在未安装时仍能通过直接入口运行检查。沿用[路线图](../roadmap/ai-sdlc-plugin-roadmap.md)的真实变更、上游修订、遗漏和恢复案例，不用技能数量或 hook 数量衡量完成。
