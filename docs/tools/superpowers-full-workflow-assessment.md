## 1. 建议及适用边界

**建议把“Superpowers 开发方法 + 项目产物契约 + Agent 原生执行控制”作为下一条完整试点路线。** 当前没有证据要求再套一层 OpenSpec / Spec Kit；是否需要它们的长期规格管理或模板分发能力，可按真实缺口再决定。这里的简化是待验证的设计判断，不是已测出的维护成本优势。

“全流程使用”可以表示设计、计划、实施、验证、审查和修正都复用 Superpowers 方法。它不意味着 Superpowers 已提供业务确认、项目知识库、CI/CD、生产监测和 Colla 同步。OpenWiki、原生项目检查及外部交付系统仍承担各自职责。

| 路线 | 如何控制 | 评价 |

## 2. 对照 AI-native SDLC Playbook

Playbook 的主线是有责任归属的产物交接、验证反馈以及运行问题回到开发。Superpowers 的开发方法能服务这条主线，但需要明确其覆盖边界。下表为本方案的映射判断，依据 [Anthropic Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)。

| Playbook 阶段 | Superpowers 可复用部分 | 项目仍需补齐或保留 |
| --- | --- | --- |
| Plan（意图） | brainstorming 的访谈、范围与替代方案讨论方法 | BA 形成并确认 Intent；已有 BA 结果直接复用，不能让开发 Agent 重新猜测业务接受 |
| Design | brainstorming 的现状调查、方案比较、自查 | Spec 明确要求、验收、Design、适用 ADR、未知项及工程接受依据；与业务 Intent 分开负责 |
| Build | writing-plans、subagent-driven-development、worktree 方法 | Plan 的正式落点、任务状态及实施授权；真实工作区基线和明确的子代理交接 |
| Test | test-driven-development、systematic-debugging、verification-before-completion、review 方法 | 有效测试标准、完整变更验证、配置本身的回归；反馈循环与独立终审分别完成 |
| Deploy | code review、finishing-a-development-branch 的部分交接方法 | MR/CI、发布与回滚、合并后收尾由实际平台执行；分支收尾不等于环境发布成功 |
| Maintain | systematic-debugging 可处理已进入调查的故障 | 事件入口、运行证据、处置权限、恢复确认与复盘；当前无生产告警，保留后置边界 |

继续沿用已确认的主动差异：本地 MVP 不强制提交；既有授权和接受依据直接复用；BA 先生成 Intent 再经 MCP 同步 Colla；真正合并和整项范围验收满足后才整体收尾。参考文章里的默认 Git 审批过程，不自动增加本项目每步重复批准。

## 3. 阶段契约：输入、允许修改、输出、转移条件

**入口先选定当前产物和范围，再调用对应方法。** 不把一次聊天历史作为下游唯一输入。路径可以保留 Superpowers 原生 specs/plans 目录，也可以映射项目既有变更目录；只维护一处正式内容，不复制两套 Spec/Plan。Design 附件可以保留并明确归属。

| 阶段 | 必须读的输入 | 允许产出/修改 | 满足什么才可进入下一步 |
| --- | --- | --- | --- |
| Intent | 原始诉求、BA 已有规则/原型与确认来源 | Intent 的问题、目标、范围、约束、采用来源及未决项 | 业务内容在对应范围已获确认；未决部分明确，不猜测批准 |
| Spec / Design | 有效 Intent；相关 OpenWiki 页；关键源码；适用 ADR 和原型原文 | Spec 及所属 Design 附件；需要演进 ADR 时按已有责任处理 | 行为、验收、设计及风险明确；关键决定有接受依据；实施受影响的未知项已解决或隔离 |
| Plan | 当前 Spec、采用的工程约束、实际源码/工作区、可运行检查 | Plan 的任务、文件/接口、依赖、检查、四态及接续说明 | 工作可执行、验证足以判定结果、当前范围有有效实施授权 |
| 实施 | 指定 Task 原文；Spec 的相关要求与全局约束；接口事实；当前差异 | 任务范围内代码、测试与必要文档；实际检查报告 | 实现者交回可审查结果；其 DONE 仅表示交回，不能直接完成 Plan |
| 验证与审查 | 当前 Spec/Plan、完整受检差异（含未提交/新增文件）、真实检查证据 | 发现、结论、证据引用；由主 Agent 汇总到既有 evidence | 验收和规范均满足；有效质量问题已解决；检查与当前受检状态相符 |
| 修正与本地交接 | 审查发现、有效输入、修正后差异、需要更新的知识 | 必要修正、受影响复验、Plan 状态、知识维护与交接结果 | 必需工作和检查完成；剩余事项不影响所声明的完成范围 |

这是每阶段的职责边界；表格本身不产生操作系统权限。需要强制边界时，按下一节配置并实测。有效问题不能因达到修正轮数、token 预算或子代理退出而变成完成。

### 最小交接内容

复用现有产物“输入依据/交接”章节，给下游以下六项即可，不另建一套阶段数据库：

1. **本次对象和范围**：变更/Task、仓库及工作目录。
2. **权威输入**：路径、已采用修订与关键章节；涉及未提交内容时记录实际工作区依据。
3. **约束与接口**：适用 ADR/项目规则；需要保持的精确值和前序接口。
4. **允许动作与输出落点**：可以修改的范围，所需权限和已有授权边界。
5. **完成证据**：本阶段应有的产物、检查或审查结论。
6. **未决与回退**：缺少上下文、需要上游决定、验证失败分别如何接续。

Spec 变更涉及验收含义时，先复核 Plan 和受影响证据，再接续；不机械重跑全部阶段。缺陷在实现则修代码，计划缺陷回 Plan，设计缺陷回 Spec，业务承诺变化回 BA/Intent。只有相关范围暂停，已授权独立工作继续。

## 4. Agent 内置机制分别承担什么

这里以用户指定的 Claude Code 文档为具体设计参考。Codex 等宿主需要重新核验可用工具与权限，不宣称配置通用。[Best practices](https://code.claude.com/docs/en/best-practices)强调简短常驻上下文、按需 Skills、独立调查/审查上下文以及可执行反馈；具体机制限制以[专项核验](../../research/execution/claude-native-stage-controls.md)为准。

| 内置机制 | 用于本方案 | 不应据此推断 |
| --- | --- | --- |
| CLAUDE.md / 项目入口 | 放最短导航、产物权威、常用命令和全局边界；详细规则按需读取 | 长篇常驻提示不能替代权限；不能假设每类子代理都会加载同一份内容 |
| Skills | 阶段方法、模板和所需上下文；显式入口比只依赖描述自动匹配更容易检查 | 安装不等于调用；`allowed-tools` 是免提示授权，不是工具池白名单 |
| 原生子代理 | 独立调查、任务实施、独立审查；交付摘要和结果路径 | 新上下文不等于文件系统隔离；不能假设继承主会话历史或其已加载 Skills |
| tools / disallowedTools、权限规则、sandbox | 限定读取者、写入者和外部动作；需要硬隔离时限制所有实际写入通道 | 保留任意 Bash/MCP 执行能力的角色，不因去掉 Edit/Write 就成为只读 |
| Plan mode | 探索与讨论计划，准备可接受的实施方案 | 不能直接等同“可写所有规划文档、绝对不能写代码”；实际限制依宿主、模式和配置而变 |
| 原生任务列表 | 当前运行的待办、依赖和调度提示 | 任务 complete 不是已验证的工程结论；与 Plan 不建立双向独立权威 |
| resume / compact / checkpoint | 接续会话、减少重复上下文、辅助恢复编辑 | 会话摘要不替代正式产物；checkpoint 不覆盖所有 Bash/外部副作用 |
| hooks | 在技能调用时注入项目背景；有独立需要时再对明确事件执行有限检查 | 注入不等于实际读取；Stop/SubagentStop 不证明业务完成；事件覆盖、错误和超时语义要分别核验 |
| headless / structured output（以后需要时） | 自动运行时返回可解析结果，便于已有流水线消费 | 格式满足 JSON schema、进程退出0都不证明内容正确或实际副作用完成 |

### 4.1 建议的执行分工

- **主 Agent 管交接。** 读取有效上游，分派有限任务，核对结果，并维护正式 Plan；不维护另一份独立完成状态。
- **调查和审查用独立上下文。** 只给当前问题、原文路径、范围和输出契约，不复制全部聊天记录。审查者能直接读取原始 Spec 和当前源码，不只读实施者的自述。
- **实施按有独立交付物的任务分派。** 同一批相似微小修改可合并；有依赖的代码工作顺序进行，不能因有子代理就同时写同一工作区。需要并行写入时另用 worktree 并验证合并结果。
- **受控读取角色不开放任意执行工具。** 以 Read/Glob/Grep 等读取能力为基础；需要跑测试时交给有对应执行权限的验证角色。报告可由读取角色返回、主 Agent 写入，避免为了保存 review.md 给审查者广泛写权限。
- **项目级定义承接控制。** 需要自定义子代理权限/hooks 的 Claude Code 方案，优先核对 `.claude/agents/` 的实际支持，不假定插件内同字段生效。父权限模式的覆盖关系也必须验证。

阶段切换时清理无用上下文，而非每个 Skill 都强制新开会话。设计讨论可以连续；实施与独立审查保持清楚边界；修复一般接续原实施者，反复无进展再换上下文或调整任务。模型选择先满足质量回归，费用不能替代通过条件。

### 4.2 hooks 的最小职责

当前先采用[独立上下文 Hook](project-context-hook-plugin-design.md)：`PreToolUse:Skill` 与 `UserPromptExpansion` 覆盖两种调用路径，只注入有界规则和实际入口，并检查 Agent 是否真正读取和采用。它不阻断调用、不改权限、不维护阶段状态。

下表是以后需要强制机械约束时的独立候选，**不属于上下文插件首版**。先用明确交接和已有检查演练，再按实际缺口增加：

| 位置 | 可检查的具体内容 | 失败后处理 |
| --- | --- | --- |
| 写入前 / PreToolUse | 文档阶段不写业务源码；实施者不改已接受的上游；动作在当前授权范围 | 阻止这次受覆盖的调用，给出允许路径或回到正确阶段；必须测试 Edit/Write、shell、MCP 等实际通道 |
| 写入后 / PostToolUse | 已选文档结构检查或局部 lint；记录哪些输入/证据需要复核 | 返回检查结果；工具已执行，不能称为撤销或未发生 |
| 阶段交回 / Stop、SubagentStop（按实际事件能力） | 输出文件可定位、必要检查结果存在且适用于受检内容 | 缺项就补；受阻就如实交回，不能用无限阻止结束代替处理阻塞 |

确定性脚本只能证明编码过的判据；模型型 hook 仍有模型判断的不确定性。当前文档还有 Stop 连续阻断上限、超时/普通失败可能放行等条件，因此强制保护不能只押在 Stop 上。发布和共享系统副作用应依实际权限、受控入口及 CI/平台判据决定。

### 4.3 最小配置应长什么样

知识接入首版由独立插件和项目 `.ai/context.json` 承担；CLAUDE.md 保留既有短导航与权威约定，无需改写原版 Skill。完整工作流仍复用现有产物契约，说明“定位当前变更 → 核对输入 → 调用阶段方法 → 核对输出 → 接续或回退”；这可是一份项目文档，不必新建总控 Skill 或七个阶段 Skill。

工具能力先区分读取角色和执行角色；调查与审查可复用同一类只读工具配置，但使用彼此独立的上下文。主 Agent 在授权范围内写正式文档和 Plan 状态，执行角色修改任务范围代码并运行检查。需要硬性路径边界时，再对实际写入工具配置路径权限/有限 hook，并验证所有开放通道。

`brainstorming`、`writing-plans` 和 `subagent-driven-development` 按当前阶段调用；上下文插件分别适配模型调用与用户直接命令。尤其 SDD 本身是协调方法，不应整套塞给每个实施子代理，导致再次拆任务、重复审查和第二套 ledger。实施者接收任务原文及必要测试/调试方法；审查者接收原始要求、实际差异和审查方法。需要自动接续的阶段入口不能一律设置 `disable-model-invocation: true`，否则模型无法调用；该字段只留给确实要求用户手动触发的入口，实际外部动作权限仍单独控制。

这些是配置边界建议，尚未生成或启用新的 Skills、agent 定义或 hook。

## 5. Superpowers 原版中要明确处理的差异

以下是已读固定版本中的具体内容，不是对整个项目质量的泛化评价。

| 默认方法/脚本 | 与当前方法的差异 | 建议处理 |
| --- | --- | --- |
| brainstorming：设计批准；Architectural 写并提交 design；Bounded 可只有聊天设计 | BA 的 Intent 与工程 Spec 不同；本地不强制提交；已有授权不重复审批 | 复用已有 Intent；Spec 含 Design，统一落点与接受责任。简单变更可以简短，但不能遗失已约定的必要交接依据 |
| writing-plans：详细代码/TDD步骤、频繁提交、默认路径 | Plan 可能过度预写实现；步骤模板可能把 commit 变成完成前提 | 保留明确接口、检查和可执行性；按任务风险决定所需细节，落实现有本地交接规则 |
| SDD 的 progress.md 与 todo | 原版 ledger 完成行是恢复依据；本项目 Task 状态以 Plan 为权威 | ledger 若保留，只作可重建运行指针，正式进度与重要决定回到 Plan/Spec 和 evidence；本地交接不得删除唯一证据 |
| task-brief 只抽取 Task N 段 | 默认不自动带上 Plan 顶部 Spec 引用及全局约束 | 调用者显式传来源章节、全局约束和前序接口；brief 为派生内容，禁止独立改成另一份需求 |
| review-package 比较 BASE..HEAD | 未提交/未跟踪内容不在该 commit 区间 | 提供包含真实受检工作区的完整差异，并区分原有用户工作；不以空 commit diff 证明“无变更” |
| SDD 自主 ruling、五轮后 park 并完成 Task、终审限制修复轮次 | 超出范围的决定可能未回上游；轮数耗尽不能降低质量门槛 | 轮数到限改为诊断、重新拆分、换上下文或转负责人；有效阻断问题未解决就保持未完成/受阻 |
| 自动选较便宜模型、严格 TDD/验证规则与各模板措辞 | 当前明确质量优先；不同任务需要不同有效检查；相同受检状态的证据可复用 | 先固定质量标准并验证模型配置；可复现缺陷先证明失败；只对实质改变/疑点补验，避免无理由重复测试 |
| finishing 的分支整合与清理 | 本地交接不是默认合并/推送/删除分支 | 明确当前终点；已授权整合才进入相应操作，MR 合并后的 Colla/Intent 收尾另走原规则 |

## 6. 放到币种校验试点里，会怎样执行

以下为建议交接示例，不是新一轮已运行结果。

```text
阶段：Spec
输入：已确认币种一致性 Intent；原 Order/Money/Pricing 行为；相关 ADR
输出：当前变更的 Spec（行为、AC、Design、边界、接受依据）
写入边界：该 Spec/明确归属附件；不实施 Java 代码
可进入 Plan：明确混币与请求币种不符的处理，保留既有订单校验与折扣
回退：若想引入换汇或改业务接受规则，返回 Intent/负责人

阶段：实施指定 Task
输入：当前 Spec；Plan 的任务原文与全局约束；实际工作区
输出：Pricing 校验及覆盖其行为的测试；真实检查报告
写入边界：Plan 指定代码/测试范围；不静默改 AC、既有有效测试或政策
交回：报告差异、检查命令/结果、受检状态、未解决问题
完成：独立审查核对源码与 Spec，主 Agent 再更新 Plan
```

开始采用时用已有 A2 起点或已明确的当前基线，不能把 A3 已修好的代码交给 Agent 后声称它独立完成了实现。有效旧结果可以用于对照与避免重复调查，但新的配置读取、权限和恢复行为需要自己的证据。

## 7. 什么需要试点证明

先跑一条正常主线，再测少量会决定采用的失败场景：

- 已确认 Intent 正确继承，Spec/Plan 各自写到唯一位置；既有授权没有被无理由重复询问。
- 缺少上游或采用旧修订时能发现；相关范围不进入实施，允许独立调查继续。
- 文档角色尝试写源码、实施者尝试改已接受 Spec 时，目标宿主确实按配置阻止；其他可写通道不绕过声明的边界。
- 中断发生在“代码已改、Plan 未更新”之间时，从实际差异和证据恢复，不重复做或误记完成。
- 全勾、旧测试报告、有效测试被削弱、遗漏未跟踪文件、子代理口头 DONE 均不能骗过完成判断。
- 到修正轮数上限仍有有效质量问题时，保持未完成并正确路由；不 park 后自动宣告已满足验收。
- Spec 上游修订只复核受影响工作，独立审查读取正确原文；本地交接保留必要证据与知识待维护信息。

试点记录宿主版本、实际加载的技能/权限配置、输入基线、真实检查和人工介入。通过后再讨论是否比当前组合更易维护；本轮没有执行这些用例，也没有正式替换现有方案。跨宿主、团队交付、MR/Colla 和生产维护分别沿既有路线图验证。
